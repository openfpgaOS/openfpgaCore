# GPU 3D — Variant System & Pipelined Fragment Processor

Living design log for the GPU work in this session. Complements `upgrade.md`
(which covered the earlier setup-FSM rolling refactor) — pick up from here in
the next session.

---

## Goal

Two GPU variants:

- **Lite** — span renderer optimized for 2.5D software engines (BSP/portal
  renderers, affine/perspective-subdivided span drawers). Span path only
  (no triangles). Built into the Pocket bitstream.
- **Full** — Lite plus 3D triangle rasterizer, Gouraud (vertex color), bilinear
  filter, alpha blending. Kept compilable for Verilator coverage and future
  hardware targets; Pocket does not ship it.

Both variants share `gpu_core.v` via per-feature `\`ifdef` flags derived from a
single variant macro. The texture cache is shared (and pipelined for both).

## Phase 0 — Variant scaffolding (DONE)

Set up the macro/feature/test infrastructure so we can build, test, and ship
both variants from a single tree.

### Macro mechanism

`src/fpga/common/gpu_features.vh` — included from `gpu_core.v` and
`axi_periph_slave.v`. Translates one of `GPU_VARIANT_LITE` /
`GPU_VARIANT_FULL` (passed via `--verilog_macro` from Quartus, or
`+define+GPU_VARIANT_*` from Verilator) into per-feature flags:

```verilog
`define GPU_FEAT_TRIANGLE        // S_TRI_* edge-function rasterizer
`define GPU_FEAT_VCOLOR          // R gradient (Gouraud)
`define GPU_FEAT_BILINEAR        // 4-tap texture filter (placeholder)
`define GPU_FEAT_ALPHA           // alpha / additive blend (placeholder)
`define GPU_FEAT_PERSP_SPAN      // Quake-style perspective spans
`define GPU_FEAT_FRAG_PIPELINE   // 1-px/cycle pipelined frag processor
```

**Defaults if no variant macro is defined:** `GPU_VARIANT_LITE`. The Pocket
Makefile passes nothing, so `make build` from Pocket = Lite. The Verilator
test bench passes `+define+GPU_VARIANT_FULL` for the `gpu-full` binary.

**Currently shipped feature flags by variant:**

| Feature | Lite | Full |
|---|---|---|
| `GPU_FEAT_TRIANGLE` | — | ✓ |
| `GPU_FEAT_VCOLOR` | — | ✓ |
| `GPU_FEAT_BILINEAR` | — | ✓ (placeholder) |
| `GPU_FEAT_ALPHA` | — | ✓ (placeholder) |
| `GPU_FEAT_PERSP_SPAN` | ✓ | ✓ |
| `GPU_FEAT_FRAG_PIPELINE` | ✓ | — *(see Phase 2 notes)* |

> **Why `GPU_FEAT_FRAG_PIPELINE` is Lite-only:** Full's triangle rasterizer
> reuses the sequential `S_SPAN_*` fragment FSM via `S_TRI_FRAG`. Refactoring
> the triangle path to feed the new pipeline is a separate project. For now,
> Full keeps the old fragment FSM (which still benefits from the new pipelined
> tex cache transparently — the cache interface is backward-compatible).

### Test infrastructure

- `obj_dir_gpu_lite/Vtb_gpu` — `+define+GPU_VARIANT_LITE` (no triangle tests)

## Phase 2 — Pipelined fragment processor (DONE for Lite)

Replace the sequential 12-state span FSM with a 4-stage pipeline targeting
1 pixel/cycle on the hot path (textured spans + colormap + FB write, no Z).

### Texture cache rewrite

`src/fpga/common/gpu_tex_cache.v` — same external interface, new internals:

- 2 stages internally: tag/data read in stage 1 (combinational address
  presentation, registered M10K result), hit detect + response in stage 2.
- **Combinational hit response** (`assign resp_valid = pipe_hit || fill_resp_valid;`)
  — gives 1-cycle req→resp latency on hits.
- **`pipe_valid` is HELD** (no default clear) — critical fix. If the consumer
  is stalled by some downstream condition (e.g. FB flush), `resp_valid` stays
  high until the consumer can capture it. Without this, downstream stalls
  silently lose tex responses → pipeline hang.
- Miss path unchanged: enters `S_FILL_AR` → `S_FILL_DATA` → `S_FILL_OUT` for
  AXI burst fill, emits a 1-cycle `fill_resp_valid` pulse on completion.
- Backward-compatible: the old single-request consumer (Full's triangle path
  via `S_SPAN_TEX_REQ` etc.) still works against the new pipelined cache.

### Pipelined fragment processor (Lite)

New state `S_FRAG_PIPE` in `gpu_core.v`. Active when `GPU_FEAT_FRAG_PIPELINE`
is defined (Lite only). Replaces the old chain
`S_SPAN_PIXEL → TEX_CALC → TEX_REQ → TEX_WAIT → CMAP → CMAP_WAIT → ZREAD → ZWAIT → ZCMP → ZWWAIT → FB → STEP`.

**Stage layout (4 register banks + a tail FB sub-FSM):**

```
S0 (Issue, comb)     drive tex_req_valid/addr from current sp_*
                     commit on (tex_req_valid && tex_req_ready) same cycle
                     latch p1, advance sp_*
                          ↓
p1  (just decided)   metadata of pixel just committed (cache RAM is reading)
                          ↓ 1 cycle later
p2  (tex captured)   tex_resp_data merged into pixel; cmap_rd_addr issued
                          ↓ 1 cycle later
p2b (cmap latency)   no-op shift — gives cmap BRAM its read cycle
                          ↓ 1 cycle later
p3  (cmap captured)  cmap_rd_data merged in; final color ready
                          ↓
fbss (sub-FSM)       FB_acc accumulate (fast path, 1 cycle/pixel)
                     or word-boundary flush (multi-cycle, stalls upstream)
```

**Combinational `tex_req_*` drive** (LITE only — ifdef'd):
```verilog
wire fp_pipe_stall = (p1_valid && !tex_resp_valid) || (fbss != FBSS_IDLE);
assign tex_req_valid = (state == S_FRAG_PIPE) && fp_have_pixel
                    && !src_done && !fp_pipe_stall;
assign tex_req_addr  = fp_tex_addr_full[25:0];
```

Old reg declarations are gated `\`ifndef GPU_FEAT_FRAG_PIPELINE` so Full's
sequential FSM can still drive them via NB writes.

**Stall conditions (the only two paths that pause the pipeline):**
1. `p1_valid && !tex_resp_valid` — tex cache miss in flight. The held
   `pipe_valid` in the cache means the response will eventually be visible
   (after fill), at which point this clears combinationally.
2. `fbss != FBSS_IDLE` — FB write sub-FSM is in `FBSS_FLUSH_W_RSP` waiting on
   AXI b-response after a word-boundary cross.

**Sub-FSM `fbss` states:**

| State | Purpose |
|---|---|
| `FBSS_IDLE` | Default. Process `p3` if valid: fast accumulate or trigger flush. |
| `FBSS_FLUSH_W_RSP` | AW/W handshakes + wait for B response. On B, apply queued pending pixel and return to IDLE. |

`FBSS_ZREAD/ZWAIT/ZWRITE/ZWRWAIT` are reserved (and declared) for when Z
support is added to the Lite pipeline — currently unused since Lite span tests
don't exercise Z (classic 2.5D engines sort on the CPU and don't touch
the hardware Z buffer).

### Phase 2 — Bugs found and fixed (the hard-won lessons)

1. **2-cycle cache req→resp latency with registered `resp_valid`.**
   First attempt had `resp_valid` as a registered output. M10K RAM read +
   registered output = 2 clock latency. Tried to add a `p1b` no-op stage to
   compensate. **Fix:** make `resp_valid` and `resp_data` combinational (wires
   driven by `pipe_hit` + the byte/halfword extract from `rd_data`). Now hit
   path is 1 cycle. Removed `p1b`.

2. **Cmap BRAM also has 2-cycle effective latency.**
   `cmap_rd_addr <= ...` (NB) → `cmap_rd_data <= cmap_bram[addr]` (NB on next
   posedge) → cmap_rd_data visible to consumer the cycle after that.
   First version merged cmap result in `p3 <- p2` shift one cycle too early
   and got off-by-one pixels. **Fix:** added `p2b` no-op stage between p2 and
   p3. p2 issues `cmap_rd_addr`, p2b is the BRAM read cycle, p3 captures
   `cmap_rd_data`.

3. **Cache cleared `pipe_valid` every cycle in `S_PIPE`.**
   Original cache had `pipe_valid <= 0` as the default in S_PIPE (only
   overridden by a new request latch). When the consumer was stalled (FB
   flush in progress), it didn't issue a new request, so `pipe_valid` cleared
   — and the in-flight tex response was silently lost. After the stall ended,
   the consumer was waiting for a response that would never come → pipeline
   hang. **Fix:** **don't default `pipe_valid <= 0`** in S_PIPE. Hold it
   until either a new request arrives (latch overwrites it) or a miss is
   detected (explicit clear). Combinational `resp_valid` then stays high
   across the consumer's stall, ready to be captured when the stall ends.

4. **`p3_valid <= 0` in `FBSS_FLUSH_W_RSP` lost the post-flush pixel.**
   When the flush triggered, the pipeline ALSO shifted in the same cycle (no
   stall yet, since `fbss` was registered IDLE). After the shift, `p3` already
   contained the NEXT pixel. Clearing `p3_valid` when the flush completed
   erased that pixel. **Fix:** don't clear `p3_valid` in `FBSS_FLUSH_W_RSP`.
   Instead, the conditional clear lives in `FBSS_IDLE`'s processing branch:
   only clear if `fp_pipe_stall` is high this cycle (meaning the pipeline
   shift won't fire to overwrite p3 naturally).

### Phase 2 results — clean Quartus build

| Metric | Pre-Phase-0 | Phase 0 Lite | **Phase 2 Lite (pipelined)** |
|---|---|---|---|
| **ALMs** | 18,312 (99%) | 13,526 (73%) | **12,907 (70%)** |
| **ALM headroom** | 168 | 4,954 | **5,573** |
| **DSP blocks** | 28 / 66 | 11 / 66 | **11 / 66** |
| **RAM blocks** | 274 / 308 | 258 / 308 | **258 / 308** |
| **GPU clock Fmax** | 90.43 MHz | 90.53 MHz | **83.77 MHz** ⚠️ |
| **Top clock Fmax** | 90.43 MHz | 90.53 MHz | **113.74 MHz** |

- **−619 ALMs vs Phase 0 Lite.** The pipelined fragment processor + pipelined
  cache are *smaller* than the sequential FSM they replaced.
- **GPU clock Fmax dropped 7.5%** (90.5 → 83.77 MHz). The combinational
  `tex_req_addr` path (16x16 multiply + adds) is the most likely culprit.
  The top clock domain unrelated to this dropped its critical path
  significantly (slack opened up elsewhere — happy fitter side effect).
- **Throughput:** old sequential FSM was ~10–12 cycles/pixel (~7–9 Mpix/s).
  New pipelined is **1 pixel/cycle in steady state**, with stalls only on
  cache miss + word-boundary FB flush. At 83.77 MHz that's a peak of ~84
  Mpix/s, ~50–60 Mpix/s real-world after FB flush stalls (1 in 4 pixels) +
  cache misses. **~7–8× over the sequential FSM.**

## Pending work

### Phase 2.5 — Recover the 7 MHz Fmax loss (optional)

The combinational `tex_req_addr` path is the long combinational path we
introduced. Options:

- Register `tex_req_addr` (= a 1-cycle pipeline register before the cache).
  Adds 1 cycle of latency, requires another consumer stage register, but
  shortens the combinational path.
- Pipeline the 16×16 tex multiply through a DSP slice with registered inputs
  (Quartus will pipeline it automatically given the right `(* multstyle *)`
  attribute).

**Verdict:** not urgent. 83.77 MHz is still well above what the rest of the
system needs from the GPU clock. Skip unless we hit a real timing problem.

### Phase 3 — Quake-style perspective spans

Add `CMD_DRAW_SPAN_PERSP` (or extend the existing span flag bits). For each
span, compute `s/z`, `t/z`, `1/z` at span start + per-segment endpoints.
16-pixel affine subdivisions: at each segment start, do a reciprocal lookup
(reuse the M10K LUT we have free in Lite) and divide to get linearly
interpolated `s` and `t` for the next 16 pixels.

**Resources:** the registered DSP and the M10K reciprocal LUT are currently
unused in Lite (they're behind `\`ifdef GPU_FEAT_TRIANGLE`). When persp_span
is added, change `gpu_features.vh` so `GPU_HAS_RECIP_LUT` is also defined for
`GPU_FEAT_PERSP_SPAN`, and unwrap those declarations.

**Estimate:** ~1.5–2k ALMs. Easily fits in our 5,573 ALM headroom.

### Phase 4 — Refactor Full's triangle path to feed the new pipeline

So Full also benefits from pipelining. Approach:

- Refactor `S_TRI_PIX` to be a "triangle pixel feeder" that runs concurrently
  with `S_FRAG_PIPE`. Each cycle, the triangle source advances `cur_x` (and
  edge functions / attribute interpolators), and when `inside_triangle` it
  asserts a "valid" signal that the pipeline issue stage consumes (alongside
  / instead of `sp_count > 0`).
- Add `src_mode` (`SRC_SPAN` / `SRC_TRIANGLE`) handling in the issue stage so
  the source mux selects between `sp_*` and `tri_*` for tex addr / fb addr /
  z computation.
- Delete `S_TRI_FRAG` (its job — issue tex_req then fall through to span
  fragment FSM — gets absorbed into the triangle source feed).
- Delete the old `S_SPAN_*` states once Full no longer needs them.
- Add Z support to `fbss` (the FBSS_Z* state slots are already declared) for
  triangle pixels that need depth test/write.

This is a substantial chunk of work. Defer until Phase 3 ships and we have
real-world validation that the Lite pipeline behaves on hardware.

### Phase 5 — Bilinear filter, alpha blending (Full only)

Pure features for Full. Bilinear is a 4-tap sample + 3 lerps in the fragment
pipeline (~300 ALMs estimated, plus 4× cache pressure → may need a wider
cache or short read FIFO). Alpha is a fb_acc read-modify-write + blend math
(~150 ALMs).

Not a priority while Lite is the only thing shipping.

## Memory layout reminder

- **CRAM0:** OS + apps
- **SDRAM:** heap + framebuffer (1 MB triple-buffered + terminal FB)
- **CRAM1:** save slots + audio sample pool (no GPU traffic)
- **External SRAM:** Z buffer (128 KB), shared with CPU through bus mux —
  too big for M10K (we have ~500 Kbit free, Z needs 1024 Kbit)

The Z buffer being in external SRAM is what makes "true 1 px/cycle with Z"
hard. Lite gets away with 1 px/cycle because the 2.5D span workloads it
targets don't use the hardware Z buffer at all.
