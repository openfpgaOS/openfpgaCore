# Variants & Addons

This doc explains the two compile-time knobs the openfpgaOS pocket build
exposes to slice the FPGA into different feature profiles:

- **VARIANT** — a named bundle of feature toggles that produces a
  distinct bitstream (e.g. `os25.rbf_r`, `os30.rbf_r`).  One core can
  ship multiple variants on the same SD card; firmware is variant-agnostic
  and queries `HW_FEATURES` at boot.
- **Addon** (`INCLUDE_<FEATURE>` macro) — a single feature toggle.
  Variants are just curated lists of these macros.  A new feature module
  is gated with `\`ifdef INCLUDE_FOO ... \`endif` in the RTL, then opted
  in by listing `INCLUDE_FOO` in the variants that should ship it.

Macros are passed to Quartus via per-job `VERILOG_MACRO` entries (one
generated `bld/<job>/ap_core.qsf` per variant), so different variants
fit independently and concurrently without recompiling shared RTL twice.

## Build for a variant

```bash
cd src/fpga/targets/pocket
make build VARIANT=os25         # default — 2.5D games, full HW mixer
make build VARIANT=os30         # 3D / SM64 — HW vertex triangles
make build-all                  # every variant, in parallel containers
make sweep VARIANT=os30         # fitter seed search for that variant
```

Each variant gets its own:

- bitstream filename: `<variant>.rbf_r` (the Pocket caps filenames at ~15
  chars; the variant token IS the name).
- isolated build dir: `bld/<variant>/` (own `db/`, `output_files/`, qsf).
- stored fitter seed: `seeds/<variant>.seed` — committed, regenerated by
  `make sweep`, read by `make build`.
- CPU netlist: `src/fpga/vendor/vexriscv/VexiiRiscv/VexiiRiscv_<variant>.v`
  — generated by `make cpu VARIANT=<variant>` (auto-runs if missing).

## Adding a variant

Three **file drops** — no edits to any Makefile or script.  Variants are
auto-discovered from `variants/*.mk`:

1. **Its module list** — `src/fpga/targets/pocket/variants/myvariant.mk`:
   ```make
   DEFS := INCLUDE_HW_MIXER INCLUDE_TRANSLUC INCLUDE_FOO
   ```
   Each macro toggles a feature module on; macros not listed leave the
   module out.
2. **Its CPU config** — `src/fpga/vendor/vexriscv/configs/myvariant.cfg`
   (copy `os25.cfg` for the stock CPU).  Cache geometry (`ICACHE_SETS` /
   `DCACHE_SETS`), extra `vexiiriscv.Generate` flags (`EXTRA_FLAGS`) and
   the maxfan post-annotation (`MAXFAN_HINT`) all live here — this is the
   ONLY place a variant's CPU shape is set.
3. **Its seed** — `seeds/myvariant.seed` (any valid Quartus fitter
   seed, e.g. `1`).  `make sweep VARIANT=myvariant` will refine it.

Then:

```bash
make cpu   VARIANT=myvariant    # generates VexiiRiscv_myvariant.v
make build VARIANT=myvariant    # → myvariant.rbf_r
make use-myvariant              # (root) make it the checkout default
```

The netlist filename stays `VexiiRiscv_<variant>.v`; the pocket Makefile
names it directly in the generated qsf.  The same registry exists on
mister (`targets/mister/variants/`, single `mister` variant today) —
`VARIANT=` is validated on every target instead of silently ignored.

> **Note:** the Pocket filename cap means variant names should stay short
> (`<variant>.rbf_r` ≤ 15 chars).  Three-letter names are safe; four is
> the practical max.

## Adding an addon (`INCLUDE_X` macro)

An addon is a feature module guarded by a single positive-include macro.
The pattern (used throughout `src/fpga/common/`):

```verilog
`ifdef INCLUDE_FOO
    foo_module my_foo (
        .clk(clk),
        ...
    );
`else
    // tie-off
    assign foo_out = '0;
`endif
```

Steps to add `INCLUDE_FOO`:

1. **Wrap your RTL** with `\`ifdef INCLUDE_FOO` / `\`endif`.  Provide a
   tie-off in the `\`else` branch so downstream consumers stay
   well-formed when the addon is absent (don't leave outputs floating).
2. **Opt variants in** by listing `INCLUDE_FOO` in the `DEFS` line of the
   relevant `variants/<name>.mk` files.  Variants that omit the macro get
   the tie-off and Quartus's `--gc-sections`-style synthesis prunes the
   dead RTL — there's no ALM cost for unused addons.
3. **(Optional) Wire a runtime cap** — if firmware needs to know whether
   the addon was compiled in, advertise it through `HW_FEATURES`:
   - Add a bit in `src/fpga/common/caps.v` (or wherever the variant
     drives the caps register).
   - Set it inside the addon's `\`ifdef INCLUDE_FOO` block.
   - Expose it in `src/firmware/api/of_caps.h` (`OF_HW_FOO`) and read
     via `of_init()` so the HAL can branch on it at boot.  See
     `OF_HW_MIXER_HW` for the worked example (HW mixer vs CPU SW mixer).

If the addon is mutually exclusive with another feature (e.g. truecolor
RGB565 displaces the palette+colormap lane), prefer a separate
`EXCLUDE_BAR` macro that gates the *other* path off — easier to read
than nested `\`ifdef` chains.  The existing os30 variant uses this
pattern (`EXCLUDE_PALETTE`, `EXCLUDE_GPU_XFORM_MAC`, etc.) where
including new HW would otherwise exceed the M10K budget.

## How macros become bitstream features (under the hood)

1. `make build VARIANT=<v>` includes `variants/<v>.mk` and resolves
   `VARIANT_DEFS := $(DEFS)`.
2. The qsf-generation rule rewrites the master `ap_core.qsf` into
   `bld/<v>/ap_core.qsf` with one `set_global_assignment -name
   VERILOG_MACRO <NAME>` line per entry in `VARIANT_DEFS`, plus a
   `VERILOG_FILE` line naming `VexiiRiscv_<v>.v`.
3. `quartus_map` reads those macros during analysis; `\`ifdef` branches
   resolve before synthesis, so unused addon RTL never reaches the
   fitter.
4. The variant-specific `<v>.rbf_r` is dropped under
   `build/pocket/Cores/ThinkElastic.openfpgaOS/`, ready for SD-card
   deployment.

Inspect what a given variant actually pulled in:

```bash
grep VERILOG_MACRO bld/os30/ap_core.qsf       # active feature flags
grep VERILOG_FILE  bld/os30/ap_core.qsf | tail -1  # which CPU netlist
```

## Caveats

- Macros are **per-variant** — they're not pocket-wide.  An `INCLUDE_FOO`
  that only one variant defines is invisible to the others.
- Mister doesn't use the VARIANT system (single bitstream per board).
- Don't add a macro just to switch between two file references — name
  the file you want directly (see how the pocket qsf-gen wires
  `VexiiRiscv_<variant>.v`; the old shim was removed because it was
  exactly this anti-pattern).
- Adding an addon is cheap in ALMs when it's unused but expensive in
  M10Ks if it instantiates BRAMs unconditionally — make sure the
  `\`ifdef` wraps any `(* ramstyle = "M10K" *)` regions too.
