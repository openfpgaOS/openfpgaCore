# Audio Pipeline Review

## Scope

Static review of the full audio path across firmware, HAL, and RTL:

- API and service surface
- Pocket target audio implementation
- Mixer HAL and IRQ flow
- Hardware mixer and output stage
- AWE / MIDI integration

No synthesis or hardware listening tests were run.

## End-to-End Pipeline

### 1. App-facing surfaces

There are currently three different playback surfaces exposed to software:

- `of_audio_*` in [src/firmware/api/of_audio.h](/home/alberto/Repos/openfpgaOS/src/firmware/api/of_audio.h:18)
- `of_mixer_*` in [src/firmware/api/of_mixer.h](/home/alberto/Repos/openfpgaOS/src/firmware/api/of_mixer.h:31)
- `of_awe_*` and `of_smp_voice` for MIDI / sample-synth playback in [src/firmware/api/of_awe.h](/home/alberto/Repos/openfpgaOS/src/firmware/api/of_awe.h:106) and [src/firmware/api/of_smp_voice.c](/home/alberto/Repos/openfpgaOS/src/firmware/api/of_smp_voice.c:26)

These surfaces overlap heavily.

### 2. Pocket target PCM path

The Pocket implementation of `of_audio_write()` in [src/firmware/os/targets/pocket/audio.c](/home/alberto/Repos/openfpgaOS/src/firmware/os/targets/pocket/audio.c:25) does not write to the hardware audio FIFO directly.

Instead it:

1. Copies mono `int16_t` samples into CRAM1 scratch
2. Flushes cache
3. Programs mixer voice 31 to play that buffer

The streaming path in the same file uses voices 29 and 30 as ping-pong buffers [src/firmware/os/targets/pocket/audio.c](/home/alberto/Repos/openfpgaOS/src/firmware/os/targets/pocket/audio.c:72).

### 3. Mixer HAL

The firmware mixer layer in [src/firmware/os/hal/mixer.c](/home/alberto/Repos/openfpgaOS/src/firmware/os/hal/mixer.c:19) is the real control plane for sample playback:

- voice allocation and stealing
- per-voice rate / loop / pan / volume
- group / master volume
- IRQ shadow tracking
- sample-pool allocation

It reserves only voice 31 for scratch playback [src/firmware/os/hal/mixer.c](/home/alberto/Repos/openfpgaOS/src/firmware/os/hal/mixer.c:21).

### 4. Hardware mixer RTL

The main audio engine is [src/fpga/common/audio_mixer.v](/home/alberto/Repos/openfpgaOS/src/fpga/common/audio_mixer.v:32).

The hot path is:

1. Scan active voices
2. Read descriptor fields from BRAM
3. Fetch 2 taps from CRAM1 through an 8-word per-voice cache
4. Linear interpolate
5. Apply log-ish volume scaling
6. Accumulate stereo mix
7. Apply optional wet-bus processing
8. Push one stereo sample into the output FIFO

Important quality-relevant pieces:

- per-voice cache and burst refill [audio_mixer.v](/home/alberto/Repos/openfpgaOS/src/fpga/common/audio_mixer.v:405)
- 2-tap linear interpolation [audio_mixer.v](/home/alberto/Repos/openfpgaOS/src/fpga/common/audio_mixer.v:1125)
- hardware volume ramp [audio_mixer.v](/home/alberto/Repos/openfpgaOS/src/fpga/common/audio_mixer.v:1193)

### 5. Output stage

The final output block is [src/fpga/common/audio_output.v](/home/alberto/Repos/openfpgaOS/src/fpga/common/audio_output.v:10).

It:

- bridges `clk_cpu` to `clk_audio` through a 1024-entry dual-clock FIFO
- serializes 48 kHz stereo I2S
- holds and decays the last sample on underrun
- applies a small post-mix boost and soft saturation

These are sensible quality-preserving protections.

### 6. AWE path

`audio_awe.v` is a second control plane layered on top of the mixer [src/fpga/common/audio_awe.v](/home/alberto/Repos/openfpgaOS/src/fpga/common/audio_awe.v:54).

It owns:

- voice state RAM
- channel state
- NOTE_ON programming bursts into the mixer
- control-rate compose stages for volume / pitch / filter / sends

`of_smp_voice` can bypass the software voice engine and drive AWE directly [src/firmware/api/of_smp_voice.c](/home/alberto/Repos/openfpgaOS/src/firmware/api/of_smp_voice.c:26), [src/firmware/api/of_smp_voice.c](/home/alberto/Repos/openfpgaOS/src/firmware/api/of_smp_voice.c:908).

## Main Problems

### 1. The PCM API is no longer honest

The public API and docs still describe `of_audio_write()` as stereo FIFO writes:

- [src/firmware/os/hal/audio.h](/home/alberto/Repos/openfpgaOS/src/firmware/os/hal/audio.h:14)
- [docs/developer-guide.md](/home/alberto/Repos/openfpgaOS/docs/developer-guide.md:442)
- [src/firmware/api/SDL2/SDL.h](/home/alberto/Repos/openfpgaOS/src/firmware/api/SDL2/SDL.h:655)

But the Pocket implementation is a mono scratch-voice playback shim:

- [src/firmware/os/targets/pocket/audio.c](/home/alberto/Repos/openfpgaOS/src/firmware/os/targets/pocket/audio.c:25)

At the same time, the raw audio MMIO register path still exists in the fabric:

- write path in [src/fpga/common/axi_periph_slave.v](/home/alberto/Repos/openfpgaOS/src/fpga/common/axi_periph_slave.v:1487)
- register definition in [src/firmware/os/hal/regs.h](/home/alberto/Repos/openfpgaOS/src/firmware/os/hal/regs.h:346)

But `core_top` does not feed those CPU writes into `audio_output`; it feeds only mixer output:

- [src/fpga/targets/pocket/core_top.v](/home/alberto/Repos/openfpgaOS/src/fpga/targets/pocket/core_top.v:2570)

This is accidental complexity and misleading API surface.

### 2. Stream voices can collide with normal mixer playback

`of_audio_stream_*()` uses voices 29 and 30:

- [src/firmware/os/targets/pocket/audio.c](/home/alberto/Repos/openfpgaOS/src/firmware/os/targets/pocket/audio.c:72)

But the allocator in `mixer.c` only protects voice 31:

- [src/firmware/os/hal/mixer.c](/home/alberto/Repos/openfpgaOS/src/firmware/os/hal/mixer.c:21)
- [src/firmware/os/hal/mixer.c](/home/alberto/Repos/openfpgaOS/src/firmware/os/hal/mixer.c:209)

So stream playback can conflict with ordinary SFX or music voice allocation.

### 3. Filter plumbing exists, but the mixer RTL does not implement it

Firmware and AWE both spend real complexity composing and writing per-voice filter state:

- `of_mixer_set_filter()` register writes in [src/firmware/os/hal/mixer.c](/home/alberto/Repos/openfpgaOS/src/firmware/os/hal/mixer.c:576)
- software filter update logic in [src/firmware/api/of_smp_voice.c](/home/alberto/Repos/openfpgaOS/src/firmware/api/of_smp_voice.c:559)
- note-on filter seeding in [src/firmware/api/of_smp_voice.c](/home/alberto/Repos/openfpgaOS/src/firmware/api/of_smp_voice.c:1085)
- AWE voice-load packing in [src/firmware/os/hal/awe.c](/home/alberto/Repos/openfpgaOS/src/firmware/os/hal/awe.c:259)

The MMIO side exposes filter fields:

- [src/fpga/common/axi_periph_slave.v](/home/alberto/Repos/openfpgaOS/src/fpga/common/axi_periph_slave.v:866)

But `audio_mixer.v` does not consume those fields in the sample path. It stops at volume ramp and wet-bus logic:

- field table through `VTBL_VOL_RATE` in [src/fpga/common/audio_mixer.v](/home/alberto/Repos/openfpgaOS/src/fpga/common/audio_mixer.v:126)
- field read FSM through phase 9 in [src/fpga/common/audio_mixer.v](/home/alberto/Repos/openfpgaOS/src/fpga/common/audio_mixer.v:977)

So the filter control stack is carrying cost without corresponding hardware behavior.

### 4. Chorus is only partially wired

`audio_awe.v` owns chorus globals:

- [src/fpga/common/audio_awe.v](/home/alberto/Repos/openfpgaOS/src/fpga/common/audio_awe.v:123)
- [src/fpga/common/audio_awe.v](/home/alberto/Repos/openfpgaOS/src/fpga/common/audio_awe.v:617)

`audio_mixer.v` expects chorus controls:

- [src/fpga/common/audio_mixer.v](/home/alberto/Repos/openfpgaOS/src/fpga/common/audio_mixer.v:85)

But in `core_top`, only reverb outputs are connected from `audio_awe`:

- [src/fpga/targets/pocket/core_top.v](/home/alberto/Repos/openfpgaOS/src/fpga/targets/pocket/core_top.v:2128)

while separate `awe_chorus_*` nets are passed into `audio_mixer`:

- [src/fpga/targets/pocket/core_top.v](/home/alberto/Repos/openfpgaOS/src/fpga/targets/pocket/core_top.v:2097)
- [src/fpga/targets/pocket/core_top.v](/home/alberto/Repos/openfpgaOS/src/fpga/targets/pocket/core_top.v:2628)

That is an incomplete integration.

### 5. Voice ownership is fragmented

Voice lifetime is tracked in several places:

- firmware shadow mask in [src/firmware/os/hal/mixer.c](/home/alberto/Repos/openfpgaOS/src/firmware/os/hal/mixer.c:31)
- hardware `voice_active` / `voice_end_pending` in [src/fpga/common/audio_mixer.v](/home/alberto/Repos/openfpgaOS/src/fpga/common/audio_mixer.v:193)
- raw IRQ pending polling in `audio.c` [src/firmware/os/targets/pocket/audio.c](/home/alberto/Repos/openfpgaOS/src/firmware/os/targets/pocket/audio.c:59)
- AWE active mask in [src/fpga/common/audio_awe.v](/home/alberto/Repos/openfpgaOS/src/fpga/common/audio_awe.v:2066)
- IRQ reconciliation in [src/firmware/os/kernel/irq.c](/home/alberto/Repos/openfpgaOS/src/firmware/os/kernel/irq.c:82)

This makes the pipeline harder to reason about than the actual DSP chain.

## Simplification Plan

### 1. Make the mixer the only playback owner

Recommended change:

- route all non-AWE sample playback through `mixer.c`
- stop programming mixer voices directly from `targets/pocket/audio.c`
- move stream voice reservation and completion tracking into the mixer layer
- use the existing mixer-end IRQ / callback path rather than ad hoc polling

Why:

- removes duplicate voice-management logic
- fixes the 29/30 collision problem cleanly
- keeps sound quality unchanged because playback still uses the same hardware mixer and output path

### 2. Choose one honest PCM interface

Pick one of these and remove the other:

Option A:

- restore a true stereo CPU-to-audio FIFO path
- wire `audio_sample_wr` / `audio_sample_data` into `audio_output`
- keep `of_audio_write()` as documented

Option B:

- formally redefine `of_audio_*` as mixer-backed helpers
- update the API/docs/SDL shim to match actual behavior
- delete the dead raw audio MMIO write path

My recommendation: Option B unless there is a strong use case for raw stereo PCM bypassing the mixer. It removes more complexity without touching the audible path users actually rely on.

### 3. Reserve voices centrally

Introduce a small reservation model in `mixer.c`:

- reserved voice 31 for scratch if scratch survives
- reserved voices 29/30 for stream if stream survives
- allocator must never hand reserved voices out

Better: if step 1 is done well, eliminate special-purpose voice ownership from `audio.c` entirely and make stream just another mixer client.

### 4. Split optional FX from the dry mixer core

Keep `audio_mixer.v` focused on:

- descriptor read
- cache / fetch
- interpolation
- gain / pan
- accumulation
- output sample generation

Move reverb / chorus into a separate post-mix block, or at least behind a clear optional boundary.

Why:

- the dry mixer is the critical always-on path
- the FX bus is the part most likely to change
- separating them reduces state-machine sprawl and makes timing work easier

Sound quality is preserved as long as the post-mix block receives the same dry stereo stream and runs at the same output rate.

### 5. Be explicit about the filter decision

There are only two sane options:

Option A:

- implement the per-voice SVF in `audio_mixer.v`
- keep the current firmware/AWE filter compose logic

Option B:

- remove the dead filter programming path from HAL/AWE/docs
- treat filtering as unsupported for now

Do not keep the current middle state. It is expensive in complexity and misleading.

### 6. Choose one MIDI/synth backend as the primary path

Right now there is:

- the older software voice engine in `of_smp_voice`
- the AWE-backed path that offloads control-rate work to fabric

If AWE is the long-term direction, simplify toward:

- AWE owns note state and per-tick compose
- mixer owns sample playback
- firmware just parses MIDI and submits state

That removes duplicated compose logic over time.

## Recommended Order

1. Fix the voice reservation bug around stream voices 29/30.
2. Decide whether `of_audio_*` is a real FIFO API or a mixer wrapper.
3. Remove dead paths that contradict that decision.
4. Decide whether filter support is real or removed.
5. Split reverb/chorus from the dry mixer core if further RTL cleanup is needed.
6. Continue converging on AWE as the single control-rate backend if that remains the product direction.

## Bottom Line

The sound-producing core is already reasonably simple:

- cached sample fetch
- linear interpolation
- per-voice gain / pan
- stereo accumulation
- FIFO to I2S

Most of the avoidable complexity is in duplicated control planes and half-retired interfaces:

- fake FIFO API vs mixer-backed implementation
- direct voice programming vs mixer HAL vs AWE
- dead filter surface
- half-wired chorus
- split voice ownership

Simplify those first. That will materially reduce complexity without touching the parts that currently protect sound quality.
