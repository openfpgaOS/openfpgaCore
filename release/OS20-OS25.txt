OS20 / OS25 optimization qualification — 2026-10-30

The current campaign is documented in:
  tools/experiments/os20_os25_remaining_20261030/README.txt
Its portable functional recipes and physical-results.json record both retained
and rejected candidates. Timing estimates are not timing closure at 100 MHz,
and synthetic CPU improvements are not measured game FPS improvements.

OS20
The dual-issue CPU now uses radix-4 integer and floating-point division.
Integer DIV/REM loops take about 21.2 rather than 37.2 cycles per operation;
dependent fdiv.s takes 19.1 rather than 32.1. Multiplication and square-root
latency are unchanged. The identical mixed CPU/interrupt/scanout workload takes
1,540,793 rather than 1,630,748 cycles (5.516% fewer). Architectural results,
cache traffic, interrupts, signed division edge cases and scanout all pass.

Seed 35 uses 16,468 ALMs and 228 M10Ks. Four-corner analysis estimates
95.26 MHz, with setup -0.498 ns at the configured 100 MHz and worst hold
+0.042 ns. Used cross-clock/input setup and recovery/removal/pulse-width
checks pass. No timing exceptions were added. The old CPU rebuilt against
the same current fabric estimates 92.65 MHz and fails a used video hold path;
that control is not a deployable fallback. This is a targeted comparison at
the saved seed, not a new full sweep.

OS20 retains I32/D64 caches, its 4-slot/32-op store buffer, full bypass,
32-voice audio, Analogizer, Dock input and affine palette/translucency support.
Diablo and ScummVM render mainly on the CPU. Variable division occurs in their
code, but its dynamic share has not been measured here. Existing application
ELFs can benefit from faster division without an ABI or compiler change.

OS25
Radix-4 division, CPU command-ring uploads, framebuffer write bursts, per-bank
SDRAM open-row tracking and dedicated span multiplication were already active.
I32/D128 caches and the single-issue CPU remain unchanged. The fresh saved-seed
control estimates 96.87 MHz, with setup -0.323 ns and worst hold +0.078 ns,
15,490 ALMs and 296 M10Ks. It preserves instruction/GPU cycle behavior; a
better physical timing estimate alone does not increase configured clock/FPS.
This control is the selected SDK build. Final physical results and SDK hashes
are recorded alongside the recipes. No new OS25 game FPS gain is established.

GPU acceptance now includes the actual dedicated-span-multiplier macro and
translucency checks: 276 checks pass. Optional clamp staging passes pixel/cycle
equivalence under delayed memory but fails a used hold path in the saved-seed
fit and is rejected. Fetch holding/factoring, FPU match registers and audio/RAM
combinations were functionally checked and fitted; results that reduce timing
margin or fail used hold paths are not promoted.

Memory/audio candidates
Moving the synchronous full-mixer position RAM and SDRAM write buffer from
MLAB to M10K preserves behavior, including read-during-write/collision handling,
but the resulting placements regress timing. They remain unchanged. Skipping
two nonstream mixer states saves mixer work without altering PCM, but the
tested fits either fail video hold or lose timing margin for negligible CPU/GPU
benefit. OS20 per-bank open-row tracking improves a CPU-only contention case
but slows a mixed GPU case and worsens overloaded audio; it remains disabled.

Quake2 / SM64 limits
The retained OS30 Quake2 release uses separate source snapshots selected by
variants/os30.sources. Native MD2/BSP/particle submission, triangle offload and
render-cache work do not automatically apply to OS25 spans or OS20 CPU drawing.
These variants still need palette, translucency and the full general mixer.
Their I32 caches already use efficient 2048-deep banks, so OS30's rejected I64
RAM repack offers no analogous 12-M10K saving. Cache cuts are not part of this
update. The hardware-tested Quake2 and SM64 core/app pairs are preserved.

SDK compatibility
Keep the current compatible Pocket os.bin and loader.bin with the newly fitted
images: the boot ROM embedded in both fits was checked against that same OS
ELF, including its BRAM services. Only os20.rbf_r, os25.rbf_r, the default os25
ap_core.sof and runtime/MANIFEST are replaced by the scoped exporter. All other
runtime payloads remain byte-identical. This is not an SD-card deployment.
