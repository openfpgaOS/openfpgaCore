Phase 10: remove the CPU vertex-preparation bottleneck
====================================================

Status: active private implementation. No new deployable core, demonstrated
frame-rate improvement, sibling publication, SD update, or seed sweep.
The retained F11 application and retained core remain the comparison baseline.

The user rejected another device trial of the sub-1% F11 change. This phase
therefore screens alternatives in software/RTL and measures the complete core
budget before proposing another Pocket image.

Findings
--------
F11 gameplay model: gfx_sp_vertex is about8.94ms/frame (29.45% CPU self time),
indexed-run preparation4.31ms, cache batching1.73ms. These are model costs,
not promises of recoverable wall-clock time. Actual retained-CPU kernel replay
finds roughly202 cycles/vertex warm,333 data-cold and436 both-cold; heavy
memory contention raises the cold cases. About95% of observed D-cache misses
are capacity misses, so a small address-layout change cannot eliminate them.

Memoization, filtered culling, index reservation and pure GPU-cull forwarding
experiments were rejected for negligible or negative modeled benefit. Their
individual source/capture reports remain under the phase10 measurement tree.

Implemented private components
------------------------------
* Exact native transform DAG using the retained os30 truncated-product FMA;
  correctly rounded reciprocal and one-light/unlit RGB. No general tiny CPU.
* Original24-byte vertex DMA, UV scaling, clip flags, persistent32-slot storage
  with validity tracking, partial LOAD preservation and explicit failure.
* Shared transform/lighting/cull arithmetic and reused position scratch RAM.
* One byte-enabled block RAM replaces separate normal/RGB/UV/alpha/clip arrays.
* Exact cull with six scratch words instead of a wide register file.
* Typed integer UV packet path: ((int16 UV - uint16 tile*8)<<11) + filter bias.
  The complete uint16 tile range is exact and fits signed32. This removes all
  formatter FMA requests; unexpected old floating uniforms require fallback.
* Bounded RUN precheck, atomic TRI2 rejection, private survivor list, and
  unpublished packet scratch words in the same block RAM.
* A software reference consumes actual raw descriptors and regenerates ordered
  legacy load/draw packets. This is a correctness reference, not acceleration.

* M-mode cbo.inval discards dirty lines without later writeback (verified).
* Packed result invalidation and copy cost~2.97ms/frame under nominal scanout.

  ~3.08ms/frame. Removing the copy does not remove the cache-miss cost.
These costs exclude GPU contention, MMIO launch/poll and accelerator time.

the successful probes use the retained MMIO timer at0x40000004.

LOAD-only is rejected for deployment, rather than sent to the Pocket.

Direct integration and measured limit
------------------------------------
Keep raw transformed vertices in private FPGA RAM, fetch original triangle
indices, cull before submission and emit directly into the ordered GPU ring.
The CPU retains existing material/texture side effects and rare fallback.
Synchronous LOAD completion first avoids saved-context replay on math errors;
it still overlaps prior raster work. PRECHECK has no GPU side effects. COMMIT
means ordered queue acceptance, not raster completion. Raw slots and the GPU
projected cache remain separate so a future LOAD cannot damage queued draws.

The command reader drains at most16 words into otherwise spare survivor-RAM
rows80..95 before checking triangles. It must never hold an accepted AXI burst
open while waiting for arithmetic. Rows0..63 hold accepted survivors and
64..79 hold one unpublished packet. TRI2 fallback remains atomic.

The shared W-first clip classifier saves97 standaloneALMs at unchanged4N+1
scan latency and passes the same native/random checks. This does not establish
a fitting complete frontend.

The integrated GDR1 engine now passes native arithmetic, AXI, ring ownership,
atomic abort and full color/depth checks. Fresh native-FMA baseline/candidate
captures match all721 frames, including27,657 injected LOAD failures and3732
atomic COMMIT failures. gpu-direct-native-functional-v1 records this proof.
This means scene/culling records and word counts plus eight sampled command
streams. The retained functional qsim treats os30 indexed commands as no-ops;
its color/depth hashes are not a 721-frame rendering proof. The actual eight
RTL raster frames below provide the meaningful image/depth comparison.

gpu-direct-coupled-v1 runs actual GDR/GPU/SDRAM/CRAM1 RTL with a modeled CPU:
eight exact color/depth frames, submission37.8276 ->34.1501ms/frame, throughput
improvement10.77%. LOAD3.976/PRECHECK2.101/COMMIT3.204ms of synchronous waits
consume much of the functional model's larger CPU saving. COMMIT includes
2.783ms ring-space waits. These overlap GPU work, so do not sum them with GPU
busy time. MMIO callbacks are modeled, not actual CPU AXI latency. This is not
a Pocket FPS measurement. Aggressive M2 priority changes34.1501 to34.1693ms:
it moves contention from LOAD to the GPU and provides no frame benefit.

Full retained-seed2 GDR fit fails19,828/18,480ALMs and2016/1848LABs. Compact
CSR readback, shared validity and shared LOAD/RUN DMA reduce this to19,508
ALMs/1977LABs, still1028ALMs/129LABs over capacity. No STA or bitstream exists
for either failed fit. See gpu-direct-core-v1 and gpu-direct-core-compact-v2.

CPU cuts do not solve this: queue reductions save244 CPU-system ALUTs and

I2F saves520 ALUTs but costs9-12% on several native kernels. ALUT figures are

Idle/drain investigation completed: correctness fix, no frame gain
-----------------------------------------------------------------
The old busy predicate really permits 8-16 output bytes to commit after
busy falls in unfenced clear/triangle tests. Including the existing write
drain predicate unconditionally fixes that ownership bug. All 42 independent
pixel/barrier assertions pass under quiet and delayed memory schedules.

Paired eight-frame coupled measurements remove all 239 premature idle-flush
starts and reduce idle maintenance episodes from 272 to 115. Total cache
maintenance falls from 0.462616 to 0.411173 ms/frame, but CPU frame time is
exactly unchanged at 37.827574 ms and all eight color/depth outputs match.
Texture-flush maintenance is only 0.008099 ms/frame. These costs are hidden
by CPU preparation; cache-maintenance tuning is not the speed solution.
The one-line correction is sealed privately in gpu-idle-drain-v1, with
gpu-cache-maint-observe-v2 and gpu-idle-drain-coupled-v1 providing paired
performance evidence. No production edit or device trial follows from it.

Current independent investigations
----------------------------------
* Canonical vertex UVs are signed16 values represented as float. A packed
  representation could remove conversion work and the 36-byte vertex stride;
  fractional clipping/rectangle consumers must retain their exact behavior.
* Clipped polygon fans may repeat projection and packet preparation for
  vertices shared by multiple fan triangles. Measure this duplication before
  changing the fallback path or its arithmetic.
* Actual GPU counters place about 4.93 ms/frame in the depth-read wait state.
  A proposed failed-depth fast reject covers only 29 pixels/frame and is not
  worth implementation. Review depth-window service instead. These residency
  times overlap CPU work and are not directly recoverable frame time.

Further screens completed without a deployable speed solution
-------------------------------------------------------------
packed-uv-v1 preserves native-FMA scene/cull/count records over 721 frames
and eight sampled ordered command streams. Its modeled CPU cost increases
0.740%, however: indexed preparation saves 0.092 ms/frame, while generic
triangle/clip consumers add more overhead. Do not deploy it. The independent
packed-uv-math-v1 reference exhausts 4,718,528 UV cases across all four

the requested gain. Existing guarded whole-batch culling experiments already
cost more than they save. The no-copy LOAD alias also lacks a compelling case:
only warm copy (~1.15 ms in the coupled window) is removable; invalidation

render-line32-v1 keeps 8 KiB/2 ways but halves lines to 32 bytes. Independent
cache scoreboards and eight exact color/depth frames pass. Frame time improves
only 0.274%; extra fills offset reduced write barriers. No fit is justified.

before global write drain. Its first coupled screen gains only 0.115%:
the single-transaction render cache gives AW priority, so an early AR still
waits downstream. The current bounded extension adds an explicit depth-read
priority sideband; ordinary texture/blend traffic retains existing arbitration.
Correct address dependence, cache writeback ownership and stalled-AR stability
must be preserved. A separate 32 KiB render-cache screen first measures the
upper bound with the original CPU; a 64 KiB CPU D-cache tradeoff is considered
only if that upper bound is large enough. Neither is production-qualified.

CRAM1 immutable vertex-source screen completed: reject for performance
---------------------------------------------------------------------
The raw LOAD accelerator can share the physical texture-memory controller
through a tiny locked round-robin read arbiter, with no response RAM. The
actual controller/PHY proof passes both dies, refresh delays, simultaneous
uploads, stalled grant ownership and reset. An unlocked-grant negative
control fails. See cram1-share-v1 and cram1-geometry-audit-v1.

Observed immutable vertex sources occupy145,392 bytes over all721 captured
frames (60 merged ranges); gameplay360..720 uses91,752 bytes. The source
inventory is hash-bound in cram1-source-inventory-v1. This is captured-scene
capacity, not a guarantee for every world or mutable vertex stream.

cram-source-coupled-v1 optimistically preloads these exact bytes into CRAM1,
remaps source descriptors, and excludes upload/lookup costs. Against the
matched LOD4 SDRAM source, LOAD wait falls3.929180 ->2.309000 ms/frame and
source arbitration wait1.680380 ->0.050286 ms. Yet total frame time only
falls36.252159 ->35.960023 ms (0.81%). GPU ring polling rises105,369 ->162,837

bandwidth is available, but faster vertex delivery exposes downstream work.
All eight actual color/depth buffers match, and the SDRAM control is exactly
cycle-identical to the prior LOAD-alias baseline. This fails the substantial

Current concrete qualification: real LOD5 source path and one physical fit
------------------------------------------------------------------------
The measured combined9.16% throughput gain now justifies checking physical
feasibility before another architecture expansion, although it remains below
the desired substantial gain. Root authorized exactly one saved-seed2 AREA
fit with originalCPU128KiB, same clocks, actual CRAM1 source arbiter and spanv3.
LOD5 must have a different ID from LOD4 so old clients cannot submit SDRAM
addresses as CRAM offsets. Source range is[0,16MiB), with alignment/count/end
validation; M2 becomes idle again. CPU reset must not strand chip transactions.

The real private SM64 client must reserve the top256KiB of16MiB fast texture
memory before ordinary allocations and lazily upload immutable vertex ranges.
Lookup/upload costs, pool-full/unsupported/absent-device fallbacks and source
lifetimes must be measured. Address-faithful simulation must model8MiB per die
to exercise the actual0xfc0000 pool, rather than remapping it to low memory.
There is still no production edit, completed fit, selected bitstream or SD
deployment from this phase. The full seed sweep remains deferred.

A separate read-only scheduling audit considers running next-frame game work
during current ring waits. The current Pocket port has ONE51,280-byte GfxPool,
so nesting the game loop would overwrite the display list being interpreted.
Audio also retains pointers to mutable object positions and a single pending
game-tick flag. Safe overlap would need separately owned frame storage plus
explicit game/audio/submit/retire ordering, with serialized title/transition
arenas. No nested game-loop callback or speculative simulation was added.
