openfpgaOS SDK App Portability — Baseline Audit
=================================================
Generated by Phase 1 of the SDK app portability plan.
Each entry is a leak in the public API (src/firmware/api/) that
prevents a single SDK app .elf from running unchanged on multiple
targets. Each entry names the phase that owns the fix.

ACCEPTANCE GREPS
----------------
After all phases ship, these three commands must produce ONLY entries
in the "permitted" allowlist below.

  grep -RnE '0x[0-9A-Fa-f]{7,8}' src/firmware/api/
  grep -RnE 'REG[0-9]+\s*\(' src/firmware/api/
  grep -RiE 'pocket|apf|cram1|bridge_base' src/firmware/api/

-----------------------------
- of_syscall_numbers.h            ABI namespace docs (0xC0DE0000 vendor base)
- of_syscall.h                    ABI commentary referencing 0xC0DE0000
- of_caps.h     OF_CAPS_MAGIC     four-byte 'CAPS' magic (0x43415053)
- of_services.h OF_SVC_MAGIC      four-byte 'OSVC' magic (0x4F535643)

- of_cache.h    .word 0x0000100f  fence.i instruction encoding
- SDL2/*                          SDL2 shim header constants (third-party)
- app.ld                          linker script — exempt; replaced by virtual

LEAKS — must fix
================

Phase 2 — caps/services fixed BRAM addresses
--------------------------------------------
of_caps.h:28      #define OF_CAPS_ADDR    0x00007800
of_services.h:27  #define OF_SVC_ADDR     0x00007A00
                  Inline of_get_caps() compiles 0x7800 into every app.
                  Fix: kernel passes both pointers via vendor auxv tags;
                  of_init.c constructor stashes them; accessors return
                  cached pointers; both #defines deleted from API.

Phase 3 — direct peripheral access in API headers
--------------------------------------------------
of_gpu.h:130      #define OF_GPU_BASE     0x4A000000
of_gpu.h:131      #define OF_GPU_REG(off) (*(volatile uint32_t *)(...))
of_gpu.h:133-143  GPU_CTRL/RING/STATUS/... compile 0x4A000000 into apps
of_gpu.h:177-191  inline ring helpers do MMIO directly
                  Fix: route GPU access through services table or expose
                  GPU MMIO base as a field in of_capabilities so the
                  inline ring writes go through a runtime pointer.

of_cache.h:35     #define OF_SDRAM_BASE       0x10000000
of_cache.h:36     #define OF_SDRAM_UNCACHED   0x50000000
of_cache.h:39-60  inline of_uncached() bakes the (0x50000000-0x10000000)
                  offset into every app
                  Fix: of_capabilities already exposes sdram_base; add
                  sdram_uncached_base; rewrite inline to use them.

of_interact.h:24  #define OF_INTERACT_BRIDGE_BASE 0x03FE0000
of_interact.h:25  #define OF_INTERACT_ADDR(n)     (...)
                  Fix: only used at interact.json authoring time; move
                  the macros to a Pocket-specific authoring helper
                  (targets/pocket/interact_addrs.h or similar). Runtime
                  path already uses ecall.

Phase 4 — Pocket-coupled bit layouts
-------------------------------------
of_input.h:19-34  OF_BTN_* bit positions match Pocket APF format byte-
                  for-byte, parallel BTN_* macros in hal/regs.h
                  Fix: declare OF_BTN_* canonical in of_input.h, delete
                  the duplicate BTN_* in hal/regs.h, document Pocket
                  identity translation in targets/pocket/input.c.

---------------------------------

api/app.ld:24     SDRAM    (rwx) : ORIGIN = 0x10400000, LENGTH = 48M

Phase 6 — APP_BRAM fallback (loader change, no API change)
----------------------------------------------------------
kernel/loader.c   APP_BRAM segment loaded straight to BRAM — fails on a
                  target whose physical layout has no BRAM at the v1
                  range
                  Fix: detect missing BRAM in target_platform_t, fall
                  back to leaving the segment at its LMA in SDRAM.

DOCUMENTATION-ONLY LEAKS (low priority, clean during the relevant phase)
========================================================================
of.h:32           comment lists Pocket memory sizes
of_caps.h:8       comment names "FB0_BASE, CRAM1 sample pool"
of_caps.h:70      sample_base field comment says "(CRAM1)"
of_file.h:24      "dest must be in CRAM1" — actually a runtime constraint
                  (DMA target requirement) that should be expressed
                  generically: "dest must be a DMA-target region as

KERNEL-SIDE NOTES (not API leaks but block the same goal)
==========================================================
src/firmware/os/Makefile:181-189
                  caps_table.o and services_table.o have LTO disabled
                  because the writes to fixed addresses look dead. Once
                  Phase 2 turns these into a static struct referenced by
                  pointer, the LTO carve-out is no longer needed and
                  should be removed.

src/firmware/os/kernel/loader.c:97,101
                  uses CRAM1_SCRATCH bounce buffer name — Pocket-y
                  terminology in shared kernel code; not an API leak
                  but worth renaming when revisiting.

NOT A LEAK
==========
caps_table.c, services_table.c populate the struct from
of_target_platform_t which itself comes from each target's
target_platform.h — this is the correct flow. The fix in Phase 2
just changes WHERE the populated struct lives (kernel BSS vs fixed
BRAM address) and HOW the app finds it (auxv vs hardcoded constant).

OUT OF SCOPE FOR THIS PLAN (covered by Rev. 2 of the report)
=============================================================
- hal/regs.h still hardcodes SYSREG_BASE/AUDIO_BASE/LINK_BASE/
  UART_BASE/ANALOGIZER_BRIDGE_BASE — these are kernel-internal and
  don't affect SDK app portability. They block common-os.bin, not
  common-app.elf.
- os.ld hardcodes targets/pocket/{terminal,boot}.o paths — kernel
  build only, not in apps.
- kernel/main.c, of_malloc.c, misaligned.c, syscall.c hardcoded
  addresses — all kernel-internal.

OS.BIN COMPOSITION CHECK (informational, ran during audit)
==========================================================
src/firmware/os/Makefile:152-154 builds os.bin from --only-section=.text
--only-section=.data of firmware.elf. Per os.ld, .boot/.fasttext/
.fastdata sections live in BRAM and produce boot.bin separately, while
.text/.data live in CRAM0 and produce os.bin. The targets/pocket/
{terminal,boot}.o input sections are routed to .boot, so they end up
in boot.bin only — they do NOT contaminate os.bin. Confirmed: os.bin
is closer to portable than the file paths in os.ld suggest.
